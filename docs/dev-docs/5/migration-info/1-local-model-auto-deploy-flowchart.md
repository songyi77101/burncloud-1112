## 一、设计差异

| 变更点 | 当前实现 | 本次流程设计 | 变更原因 |
| --- | --- | --- | --- |
| 下载传输 | DownloadManager 初始化会启动 aria2；自动引导依赖 Windows 资源 | 用跨平台流式 HTTP 传输，保留稳定数据库任务 ID、旧接口、取消和恢复语义 | macOS/Linux 不应要求用户安装 aria2 或额外工具 |
| 断点身份 | 已有 aria2 GID 和进度记录 | 恢复时重新核对本地部分文件和远端实体；旧 GID 不作为 HTTP 传输身份 | 防止升级后沿用不可信断点，或拼接不同版本的文件 |
| 基础运行时来源 | 仅使用 BURNCLOUD_LLAMA_SERVER 指定的程序 | 显式配置优先，其次受管缓存，再从本平台内嵌基础归档安装 | 没有预装运行时且不能访问 GitHub 的用户也可部署；不覆盖用户已有配置 |
| 运行时后端 | 现有准备器没有受管安装及完整的所选后端准备流程 | Windows/Linux 默认 CPU；macOS auto 实测 Metal，不可用则 CPU；Windows CUDA 必须主动选择且不静默降级 | 区分默认基础能力和显式加速选择，控制包体积并如实反馈设备能力 |
| 工件信任 | 手动本地路径部署直接构造已校验工件 | 旧手动入口保留；新自动部署重新核对权威目录身份，并真实计算 GGUF 摘要 | 自动链路不能仅凭客户端 URL、路径或下载完成状态建立信任 |
| 部署编排 | 客户端先下载，再发手动路径部署请求 | 服务端创建持久化父任务，模型和运行时并行准备，再启动、检查健康并接入路由 | 避免客户端长时间持有同步请求，支持刷新后的状态查询 |
| 成功边界 | 现有入口提供下载和部署各自的结果，尚无统一自动部署任务终态 | 父任务仅在健康检查、当前代次路由接入和最终结果持久化均成功后 succeeded | 防止把文件下载完成或子进程启动成功显示为“可以对话” |
| 取消与并发 | 已有下载取消和客户端旧运行结果隔离机制 | 增加父任务取消意图与完成提交的串行判定；共享准备不受单一使用者取消影响；只清理本任务自有进程/路由 | 防止双击重复启动、迟到结果覆盖取消，以及误停其他部署 |
| 重启恢复 | 下载已有持久化记录，部署事件快照主要在内存中 | 新增 SQLite/PostgreSQL 部署任务记录；重启后本机未完成任务 interrupted，不自动重复启动 | 保留可查询的失败/中断原因，并支持用户主动重试复用有效资源 |
| 部署归属 | 手动部署以模型文件名主干确定 model_id | 自动部署依据完整工件身份和后端区分归属，并核对进程代次与路由绑定 | 不同仓库的同名文件不能互相覆盖或被错误清理 |
| 发行方式 | CD 当前只构建 Windows | 四目标各嵌入唯一基础压缩包；CUDA 按需下载；构建前校验且 Cargo 构建脚本不联网 | 覆盖已确认平台，并适配现有单文件更新而不合并全部平台资源 |

## 二、保持不变的边界

- 继续保留已有模型下载接口和手动本地文件部署、查询与停止接口。
- 自动部署任务取消不替代已成功运行模型的停止操作。
- 不修改用户本机已有 llama.cpp、系统 PATH、系统库目录或驱动。
- 继续复用现有下载数据库、DeploymentService、健康探测和本地路由能力，不新增通用安装器或第二套进程管理器。
- 模型仍按用户选择后下载，不把模型合并到客户端发行包。
- 不扩大到 Linux CUDA/ARM64、Alpine/musl、用户端源码编译、远程节点、非 GGUF 转换或驱动自动安装。
